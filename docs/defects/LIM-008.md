# LIM-008: Docker on macOS cannot reach the Apple GPU, so containerised embeddings run on the CPU

**ID:** LIM-008
**Legacy:** none (restructuring plan, task P0.10)
**Kind:** limitation
**Status:** fixed
**Severity:** minor
**Class:** runtime-environment
**ODC:** n/a (limitation)
**Component:** `ai_service/Dockerfile`; `ai_service/main.py` :: `_check_embedding_sync`, `health`
**Found:** the AI service image installs CPU-only torch, and Docker Desktop on macOS exposes no GPU to containers; the demo machine is an Apple Silicon Mac
**Added:** 2026-11-14
**Fixed in:** commit `4848c62` (closed by running the AI service natively on the Mac)
**Test:** `ai_service/test_service_hardening.py` :: `EmbeddingDeviceTests`

## Statement

The demo runs on an Apple Silicon Mac. Ollama already ran natively for this
reason; the AI service ran in Docker, so BGE-M3 encoding (every guideline
chunk at indexing, and the query plus each semantic requirement at
validation) ran on the CPU. Which device the model used was not reported
anywhere.

## Consequence

Slower indexing and retrieval in the demo configuration, and no way to tell
from the outside whether the GPU was in use.

## What closed it

The Mac demo runs the AI service natively (`docs/runbook-demo-mac.md`), where
FlagEmbedding selects Apple MPS on its own. `EMBEDDING_DEVICE` overrides the
choice; the containerised service sets it to `cpu`. The device the model
actually loaded on is reported in the startup pre-flight and in `/health`
(`embedding.device`).

On the demo machine the native service reported `device=mps:0`, and a
73-page thesis validated end to end in 368 s, of which retrieval and the
model call took 367 s (one semantic batch, `qwen3:14b`).

## For the thesis

T5, and the hardware side of the `runtime-environment` class it shares with
[DEF-042](DEF-042.md). The same code runs at different speeds depending on
where it is deployed, which is exactly why the device is now reported rather
than assumed.
