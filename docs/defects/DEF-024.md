# DEF-024: the validation worker runs inside the web process and freezes every page while a job runs

**ID:** DEF-024
**Legacy:** none (restructuring plan, problem 1; task P0.1)

**Found:** architecture review of `app/main.py` for the production restructuring plan; the startup hook created the queue worker as an `asyncio` task in the web server's own event loop
**Added:** 2026-11-14

**Theme:** T7

## Symptom

While a submission is being validated, every page of the web application
stalls: the student dashboard, the admin pages and the login form all wait
until the job's PDF analysis, report rendering or e-mail delivery finishes. A
long thesis makes the whole site unresponsive for the length of those steps.

## Root cause

`startup()` in `app/main.py` ran `asyncio.create_task(queue_worker())`, so
the worker shared the uvicorn event loop with every HTTP request.
`process_job` is `async`, but most of its work is synchronous: PyMuPDF text
and layout extraction (`inspect_pdf`), the deterministic rules, SQLAlchemy
queries, ReportLab rendering (`build_validation_report`) and `smtplib`
(`send_submission_email`). Each of those calls holds the loop until it
returns; only the AI-service call itself yields.

A second consequence: with more than one uvicorn worker process, each process
started its own queue worker, and the claim in `queue_worker` (select, then
update) was not atomic, so two processes could take the same job.

## Reproduction

```
uvicorn app.main:app --port 8000      # before the fix
# submit a 100-page thesis, then reload /student/dashboard repeatedly:
# requests hang while the job is in inspect_pdf or build_validation_report
```

The regression test reproduces it without timing: it queues a job, starts the
app, and checks whether the web process took the job off the queue.

## Fix

The worker moved to its own module and process, `python -m app.worker`
(`app/worker.py`), with a matching `worker` service in `docker-compose.yml`.
The web startup only creates tables. In the worker process, blocking calls
are harmless: nothing else shares its loop, and it runs one job at a time to
match the single local model. The claim now uses `SELECT … FOR UPDATE SKIP
LOCKED`, so a second worker process can never take the same job.

## Verified

Before: a job queued before startup was `RETRYING` (picked up by the web
process, then failed on a missing file) within 0.5 s of the app starting.
After: the same job is still `QUEUED` after startup, and the worker test takes
it to `COMPLETED` with one attempt.

## Tests

The three tests named above. `test_web_startup_does_not_run_validation_jobs`
and `test_queue_worker_runs_as_its_own_service` were red on the pre-fix code
(status `RETRYING`; no `worker` service) and are green with the fix.

## For the thesis

T7. An `async def` signature says nothing about whether a function yields.
The worker looked cooperative because its one network call was awaited, while
the CPU-heavy steps around it were not. Putting the queue in its own process
makes the concurrency model explicit, which is also what [LIM-003](LIM-003.md)
asks for on the AI side.
