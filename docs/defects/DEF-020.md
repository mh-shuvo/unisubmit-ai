## Symptom

Rule 31, `heading_case` / `Section Heading` / `Title Case`, fails on headings
that are correctly title cased. Only the incorrect form passes: `Scope And
Significance` is accepted and `Scope and Significance` is rejected.

## Root cause

Title case is tested by comparing the heading against Python's `str.title()`,
which capitalises every word including articles, conjunctions and short
prepositions. Real title case does not, so the test accepts exactly the strings
that are wrong.

Latent until [DEF-009](DEF-009.md) was fixed, because an undecidable rule
previously passed silently. It is now live for any submission that numbers its
sections.

## Reproduction

See the worked reproduction in
[`open_defects.md`](../open_defects.md#reproduction).

## Fix

Replaced the `txt != txt.title()` comparison with a small title-case
implementation (`_to_title_case`, `_needs_title_case_fix`) that respects a
stop-word list (`_SMALL_WORDS`: articles, coordinating conjunctions, short
prepositions) instead of Python's blanket `str.title()`. A word is lowercased
only if it is in that list **and** is not the first or last word of the
heading; a leading section number such as `1.5` is left untouched because it
has no letters to capitalise in the first place, so no special-casing was
needed for it; a word that is already all-caps (an acronym such as `AI`) is
left as-is rather than being forced into `Ai`.

For a new contributor: the one-line summary is *"stop treating every word the
same."* `str.title()`'s mistake was applying one rule (capitalise after every
non-letter) to every word, when English title case actually has two classes of
word — ordinary words, which are always capitalised, and a short, fixed list of
minor words, which are capitalised only when they open or close the heading.
Encoding that second, smaller rule as an explicit exception list was the
smallest change that matches how the guideline itself defines "Title Case",
rather than reaching for a third-party title-case library or trying to patch
`str.title()`'s output after the fact (which would have needed the same
stop-word list anyway, just applied in the wrong direction).

A first draft of the fix (not shipped) called the helper `isTitleCase` and had
it check the whole document's text (`info['text']`) instead of the one heading
line being examined — a typo that two correctly-cased headings are enough to
expose, since `info['text']` almost never equals its own title-cased form. It
was caught in review before being committed; the final implementation always
checks the specific heading line (`txt`), and the helper was renamed
`_needs_title_case_fix` so its return value reads the right way round (`True`
means "this heading's case is wrong", not "this heading is titled correctly").

Two related vocabulary gaps in the same branch were fixed in the same commit:
`heading_case` now also recognises `'UPPERCASE'`/`'upper case'` as synonyms for
`'ALL CAPS'` (previously an unrecognised value fell through and the rule
silently passed without checking anything).

## Verified

Before the fix, the worked reproduction (see above) returned `FAIL` for both
`'1.1 Background'` and `'1.5 Scope and Significance'` — a correctly numbered,
correctly cased heading could not pass. After the fix, the same two headings
return `PASS`, and a genuinely wrong heading (`'of mice and man'`, lower case
throughout) still returns `FAIL`, so the fix is not satisfiable by weakening or
removing the check.
