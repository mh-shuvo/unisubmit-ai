# LIM-001: the services did not verify their dependencies at startup

**ID:** LIM-001
**Legacy:** none (recorded only in commit `b38c6d1`)
**Kind:** limitation
**Status:** fixed
**Severity:** major
**Class:** observability-gap
**ODC:** n/a (limitation)
**Component:** `ai_service/main.py`, startup
**Found:** accumulated across [DEF-004](DEF-004.md), [DEF-014](DEF-014.md) and

**Added:** 2026-10-27
**Fixed in:** commit `b38c6d1`
**Test:** none
**Theme:** T6

## Statement

The AI service started and answered `/health` without checking that any of the
things it depends on were actually usable. A missing Ollama model, an
unreachable Qdrant, or an embedding model that would not initialise all
surfaced later, as a failure of whichever student submission happened to arrive
first.

As the v9.10.1 notes put it: a successful health response alone does not verify
model generation, collection existence, or response correctness.

## Consequence

Every dependency problem was diagnosed through a user-visible failure instead of
a startup one. This is the common factor behind several entries in this
register, and it inflated the diagnosis cost of all of them.

## Resolution

Closed by commit `b38c6d1`, which adds fail-fast pre-flight checks before the
service serves traffic: `_check_ollama` for connectivity and model availability,
`_check_qdrant_sync` for the connection and collection access, and
`_check_embedding_sync` for `BGEM3FlagModel` initialisation, each reported in a
pass or fail banner, with `sys.exit(1)` if any critical check fails.

## For the thesis

T6. The entry is kept although it is closed, because the interesting content is
the diagnosis cost it imposed on the entries that preceded it, not the feature
that removed it. A health endpoint that reports process liveness rather than
dependency readiness is a common pattern and an actively misleading one in a
system whose dependencies are a model server, a vector database and a
locally loaded embedding model.
