## Symptom

`unisubmit migrate` on a database created by v9.14 stops with "differs from
the baseline schema" and lists every Phase 2 table and column as missing. No
existing installation could upgrade.

## Root cause

The [DEF-039](DEF-039.md) fix adopted an old database by comparing it with
the models and stamping it at the baseline if nothing differed. While the
baseline was the latest revision, "the models" and "the baseline" were the same
schema. Revision `0002` changed the models, so a v9.14 database could never
match them before it was upgraded.

The constraint renaming had the same assumption: it matched constraints
against the latest models, so a constraint that `0002` replaces
(`teachers_email_key`) was never renamed to the name `0002` drops
(`uq_teachers_email`).

The Phase 1 test did not catch it because it built its "old" database from the
current models rather than from the old code.

## Fix

- Renaming reads the database, not the models: a constraint named the way
  Postgres names it (`teachers_pkey`, `teachers_email_key`,
  `teachers_department_id_fkey`) gets its convention name. Constraints the
  models named explicitly keep theirs.
- The database is then stamped at the baseline and upgraded to head, and
  compared with the models only after that. All of it is one transaction:
  any difference or failure rolls back the renames, the stamp and the
  upgrade.
- The tests load `tests/fixtures/schema_v9_14.sql`, the schema v9.14 actually
  built (dumped from the v9.14 code), instead of simulating it.

## Verified

Both tests red before the fix, green after. A compose rehearsal on a database
and storage volume written by the v9.14 image: adopted, upgraded to `0002`,
files relocated, pages and downloads working.

## For the thesis

T8, second generation of DEF-039: a migration mechanism that was right for
exactly one revision. The test reproduced the old schema from the new code,
so it could only ever agree with it. A frozen fixture from the old release is
the honest input.
