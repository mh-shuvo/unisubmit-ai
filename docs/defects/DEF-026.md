# DEF-026: two quick uploads create duplicate version numbers and duplicate validation jobs

**ID:** DEF-026
**Legacy:** none (restructuring plan, problem 5; task P0.3)
**Kind:** defect
**Status:** fixed
**Severity:** major
**Class:** job-coordination
**ODC:** Timing/Serialisation, Missing; trigger: Logic/Flow
**Component:** `app/main.py` :: `save_queue_version`, `resubmit`
**Found:** architecture review; the next version number was computed as `len(sub.versions) + 1` with no lock and no uniqueness constraint
**Added:** 2026-11-14
**Fixed in:** commit `4848c62`
**Test:** `tests/test_queue_and_uploads.py` :: `UploadTests.test_upload_while_validation_active_creates_no_version`, `ConcurrentUploadTests.test_concurrent_uploads_never_share_a_version_number`
**Theme:** T7

---

## Symptom

A student who double-clicks "Add revised version to queue" gets two rows
called "Version 2", and the queue holds two validation jobs for them. Each job
occupies the single local model for the full length of a validation.

## Root cause

`save_queue_version` read the submission's versions, numbered the new one
`len(sub.versions) + 1`, and inserted it, with nothing serialising two
requests for the same submission. `submission_versions` has no
`UNIQUE (submission_id, version_no)` constraint, so the database accepted the
duplicate. The resubmission form is hidden while a job is queued, but the
second click of a double-click is already on its way.

## Reproduction

Two threads upload to the same submission at once against PostgreSQL:

```
TEST_POSTGRES_URL=postgresql://... python -m unittest \
  test_queue_and_uploads.ConcurrentUploadTests      # run from tests/
# before: version numbers [1, 2, 2]
```

## Fix

`save_queue_version` now locks the submission row
(`SELECT … FOR UPDATE`) before reading, so concurrent uploads for one
submission run one at a time; numbers the version from
`MAX(version_no) + 1`; and refuses a new version while a job for the
submission is `QUEUED`, `RETRYING` or `PROCESSING`, in which case `resubmit`
redirects back to the submission page with an explanation. The submission
page now shows that message.

A database constraint would be the stronger guarantee but needs a migration,
which the project does not have yet ([DEF-039](DEF-039.md)); it is task P3.8
of the restructuring plan.

## Verified

PostgreSQL, two concurrent uploads after a completed version 1: before, the
versions were `[1, 2, 2]` with two queued jobs; after, `[1, 2]` with one. With
only the lock removed again, the test returns `[1, 2, 2]`.

## Tests

`test_upload_while_validation_active_creates_no_version` (SQLite, sequential:
the double-click case) and `test_concurrent_uploads_never_share_a_version_number`
(PostgreSQL only, skipped unless `TEST_POSTGRES_URL` is set, because SQLite
cannot express `FOR UPDATE`). Both were seen red with only the lock and the
active-job check reverted, and green with them.

## For the thesis

T7. The interesting interaction is with [DEF-034](DEF-034.md): refusing an
upload while a job is active is only safe if an active job always ends. Before
DEF-034 was fixed, a job stranded in `PROCESSING` would have blocked the
student's resubmissions permanently.
