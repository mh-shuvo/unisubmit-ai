# DEF-046: the upload lock is released before the new version's job exists, so two quick uploads can still both be queued

**ID:** DEF-046
**Legacy:** none (found on branch `phase-1-tooling-layout-migrations`; introduced by the [DEF-026](DEF-026.md) fix)
**Kind:** defect
**Status:** fixed
**Severity:** major
**Class:** job-coordination
**ODC:** Timing/Serialisation, Incorrect; trigger: Concurrency
**Component:** `services/core/src/unisubmit/main.py` :: `save_queue_version`
**Found:** the DEF-026 concurrency test failed five times out of five after the switch from psycopg2 to psycopg 3 (task P1.6), with versions `[1, 2, 3]` where `[1, 2]` was expected
**Added:** 2026-11-14
**Fixed in:** commit on branch `phase-1-tooling-layout-migrations` (see `git log --grep DEF-046`)
**Test:** `services/core/tests/test_queue_and_uploads.py` :: `ConcurrentUploadTests.test_concurrent_uploads_never_share_a_version_number`
**Theme:** T7

---

## Symptom

Two uploads of a revised version a moment apart, after the previous
validation has finished, can both be accepted: the submission gets versions
2 and 3, and two validation jobs occupy the single local model one after
the other. DEF-026 was meant to refuse the second upload.

## Root cause

The DEF-026 fix locks the submission row (`SELECT … FOR UPDATE`), checks
that no job is active, and then saves the version and its job. It saved them
in two transactions:

```python
db.commit()            # version saved; the row lock is released here
db.refresh(sv)
db.add(AIJob(...))
db.commit()            # job saved
```

The first commit ends the transaction that holds the lock. A second upload
waiting on the lock gets it in the gap between the two commits, finds the
new version but no active job yet, and queues another version.

## Reproduction

```
TEST_POSTGRES_URL=postgresql+psycopg://…/scratch \
  uv run pytest services/core/tests/test_queue_and_uploads.py -k concurrent
# AssertionError: [1, 2, 3] != [1, 2]   (5 runs of 5 with psycopg 3)
```

With psycopg2 the second thread usually woke after the job commit, so the
same test passed during Phase 0: the window existed, the timing hid it.

## Fix

The version is flushed to get its ID and the job is added in the same
transaction, so one commit saves both and releases the lock.

## Verified

The concurrency test against PostgreSQL 16: red 5 of 5 before the fix, green
10 of 10 after it.

## For the thesis

T7, and a second-generation defect: the lock was right and the check was
right, but the transaction boundary between them was not. A concurrency test
that passes can still be timing-dependent; changing the database driver
changed the timing and exposed it. Qualifier `Incorrect`: the step existed but
was split in the wrong place.
