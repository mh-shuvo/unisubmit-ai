# DEF-015: concurrent Ollama consumers time each other out

**ID:** DEF-015
**Legacy:** D8 (`docs/validation_defects_and_fixes.md`)
**Kind:** defect
**Status:** fixed
**Severity:** major
**Class:** resource-contention
**ODC:** Timing/Serialisation, Missing; trigger: Concurrency
**Component:** `ai_service/main.py` :: `call_ollama`, `app/ai_service_client.py`
**Found:** running `test_job.py` while the application's `queue_worker` was
live; both jobs timed out
**Added:** 2026-10-17
**Fixed in:** v9.11, commit `6e394f9`
**Test:** none
**Theme:** T5

---

## Symptom

Two validation runs started at once and neither finished. Each timed out
waiting on generation that the other was occupying.

## Root cause

One Ollama instance serves every caller and processes requests serially. The
web application's `queue_worker` is written on that assumption, but nothing
enforces it: `test_job.py` calls `process_job()` inline and bypasses the queue
entirely, so a second consumer can appear at any time and both callers then
wait out budgets sized for exclusive access.

Batching in [DEF-014](DEF-014.md) made this worse by changing the shape of a
call, since each batch now holds the model for longer.

## Fix

Make the per-call Ollama timeout configurable as `OLLAMA_TIMEOUT`, defaulting to
900 seconds, where the hardcoded 300 seconds had been sized for single-shot
calls. Raise the client budget to `RAG_VALIDATE_TIMEOUT`, 1800 seconds, for
multi-batch runs. Name the failing batch and the exception type in the 503
detail, where the previous message stringified to empty and read
`Local LLM unavailable: ` with no reason.

## Verified

A full multi-batch run completes without timing out. The underlying contention
is mitigated, not removed: see [LIM-003](LIM-003.md).

## Tests

None. Reproducing it requires two live consumers of a real Ollama instance,
which the offline suite deliberately does not provide.

## For the thesis

T5. The fix is honest about what it is: budgets were widened so that serialised
work completes, rather than the serialisation being made explicit. The residual
constraint is carried as a limitation instead of being written off, which is the
distinction the register exists to record. Note also that the empty 503 message
is an [observability gap](DEF-003.md) recurring in a second service.
