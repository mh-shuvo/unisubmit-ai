## Symptom

Adding a column to a model works on a fresh database and fails on every
existing one: the first query that selects the column raises
`column … does not exist`, and the page returns 500.

## Root cause

The schema is created by `Base.metadata.create_all` at startup.
`create_all` creates missing tables but never alters existing ones, and the
project has no migration tool, so nothing carries a model change to a
database that already has the table.

## Reproduction

```
# add a column to SubmissionVersion, restart against the existing Postgres
# database, open a submission page: ProgrammingError, column does not exist
```

## What closing it requires

Alembic with a baseline revision taken from the current models, stamped onto
existing databases, and migrations run as a separate step before the web app
and worker start (task P1.8). Until then, constraints that would harden
[DEF-026](DEF-026.md) and [DEF-037](DEF-037.md) cannot be added safely.

## Fix

Task P1.8. Alembic, with the migrations inside the package and a baseline
revision `0001` autogenerated from the models. `unisubmit migrate` runs as its
own step (the compose `migrate` service) before the web app and the worker
start; neither creates tables any more.

A database built by `create_all` is adopted rather than recreated. Postgres
had named its constraints itself (`teachers_email_key`), while the baseline
uses a naming convention (`uq_teachers_email`), so the first attempt refused
every existing database. `migrate` now renames each constraint to the
baseline's name, matched by kind and columns, then compares the schema with
the models and stamps it at `0001` only if nothing differs. Otherwise it
lists the differences and rolls back, renames included.

## Verified

- A database built by the v9.14 code, and a schema-only copy of the demo
  database: adopted, and `pg_dump -s` identical to a freshly migrated one.
- A compose rehearsal on a v9.14 database and storage volume: adopted at
  `0001`, then the web app and worker started.
- `test_models_match_the_migrations`, `test_database_created_without_migrations_is_adopted`
  (red without the renames) and `test_database_that_differs_from_the_baseline_is_refused`.
  CI runs `unisubmit migrate` and `alembic check` on an empty database.

## For the thesis

T8. A new class, `schema-drift`: the code and the database disagree about
the schema and nothing reconciles them. It blocked part of Phase 0, which is
how it surfaced.
