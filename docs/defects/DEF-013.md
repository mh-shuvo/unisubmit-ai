# DEF-013: `>=` was validated as `==`

**ID:** DEF-013
**Legacy:** D6 (`docs/validation_defects_and_fixes.md`)
**Kind:** defect
**Status:** fixed
**Severity:** blocking
**Class:** nl-to-rule-translation
**ODC:** Checking, Incorrect; trigger: Normal Mode
**Component:** `app/format_validation.py` :: `validate_format_profile`
**Found:** a submission with compliant 14 pt body text failing a rule that asks
for at least 12 pt
**Added:** 2026-10-17
**Fixed in:** v9.11, commit `6e394f9`
**Test:** `tests/test_format_validation_rules.py` :: `OperatorSemantics`
**Theme:** T1

---

## Symptom

Body text at 14 pt failed a rule written as `>=12`.

## Root cause

Once `_parse_num_op` recovered the number from the text it was compared for
equality. The operator survived parsing and was then discarded at comparison,
so every relational rule became an exact-match rule and only the boundary value
could pass.

## Fix

Honour the recovered operator with `_num_ok`.

## Verified

`>= 12 pt` accepts 14 pt body text and still rejects 8 pt.

## Tests

`tests/test_format_validation_rules.py :: OperatorSemantics`, with
`test_at_least_12pt_accepts_14pt_body` and `test_at_least_12pt_rejects_8pt_body`
as the matched pair.

## For the thesis

T1. A guideline requirement is a predicate, not a value, and the two halves of
that predicate were lost at different points in the pipeline: the number in
[DEF-008](DEF-008.md), the operator here. Separating them is what made the
second half easy to overlook once the first was fixed, and the pair is a good
argument for parsing a requirement into a single comparison object rather than
into a number plus a convention.
