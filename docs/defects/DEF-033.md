# DEF-033: the AI service blocks its event loop on embedding and Qdrant calls

**ID:** DEF-033
**Legacy:** none (restructuring plan, problem 10; task P0.9)
**Kind:** defect
**Status:** fixed
**Severity:** major
**Class:** event-loop-blocking
**ODC:** Timing/Serialisation, Incorrect; trigger: Logic/Flow
**Component:** `ai_service/main.py` :: `rag_validate`, `index_template`, `rag_search`, `extract_format_profile`, `embed`, `rag_collections`, `delete_rag_collection`
**Found:** architecture review; `retrieve_chunks` (BGE-M3 encoding plus a Qdrant query, and a synchronous `httpx.post` on the legacy search path) was called directly from `async def` routes
**Added:** 2026-11-14
**Fixed in:** commit `4848c62`
**Test:** `ai_service/test_service_hardening.py` :: `EventLoopTests.test_probe_answers_while_retrieval_is_running`
**Theme:** T7

---

## Symptom

While the AI service retrieves guideline context for a validation, or embeds
a guideline during indexing, it answers nothing else: `/health` hangs, so the
web app's AI status page, whose health call times out after 4 s, reports the
service offline in the middle of a validation it is running.

## Root cause

The routes are `async def` and await `call_ollama`, but the steps before it are
synchronous: `retrieve_chunks` encodes the query with the BGE-M3 model and
queries Qdrant, once for the main query and once per semantic requirement (up
to 40), and `index_template` extracts the PDF, embeds every chunk and upserts
them. All of this ran on the service's event loop.

## Reproduction

The regression test starts a validation whose retrieval takes 0.6 s per call
and times a request to `/` from the moment retrieval begins:

```
python -m unittest test_service_hardening.EventLoopTests   # from ai_service/
# before: 1.21 s (the probe waited for both blocking retrievals)
```

## Fix

Every embedding and Qdrant call in an `async` route runs through
`asyncio.to_thread`. Encoding is serialised by a lock (`embedding_lock`),
because the model is shared and requests can now overlap.

Still synchronous: the PyMuPDF page parsing inside `/guideline/profile`, which
takes about a second per guideline; it moves with the service restructure
(task P6.3).

## Verified

Test: the probe waited 1.21 s before the fix and returns in well under the
0.3 s limit after it. Live, on the Apple Silicon demo machine: during a
368-second validation of a 73-page thesis by the native service, 69 `/health`
probes at 5-second intervals had a median latency of 0.17 s and a maximum of
0.89 s.

## Tests

`test_probe_answers_while_retrieval_is_running`, red before the fix (1.21 s)
and green with it. An earlier version of the test, which waited a fixed
0.1 s before probing, passed on the unfixed code because the blocking calls
had already finished; the test now times the probe from the moment retrieval
starts.
