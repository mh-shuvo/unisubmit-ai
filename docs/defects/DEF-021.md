# DEF-021: an unavailable repair service is reported as invalid model output

**ID:** DEF-021
**Legacy:** none
**Kind:** defect
**Status:** open
**Severity:** major

**ODC:** Checking, Incorrect; trigger: Complex Path

**Fixed in:** not fixed

## Symptom

When the repair call fails because the model service is unavailable, the
endpoint returns 502 with
`Semantic validation JSON invalid after one repair for every batch`. It should
return 503. An operator reads that an outage was a malformed-output problem, and
goes looking in the wrong place.

## Root cause

A regression introduced by the fix for [DEF-014](DEF-014.md) in commit
`6e394f9`. Batch isolation wrapped the repair call in a single broad
`except Exception` so that one unusable batch cannot discard the batches that
succeeded. That handler cannot distinguish a payload that will not parse from a
`call_ollama` transport or service failure, and treats both as a failed batch.
When every batch fails for the same reason, the final check raises 502
unconditionally.

The 502 against 503 distinction was established deliberately by the v9.10.1
work, [DEF-002](DEF-002.md): persistent bad output is 502, an unavailable
repair service is 503. Batch isolation is correct and the distinction is
correct; the handler collapsed them.

## Reproduction

From `ai_service`, with that directory's own virtual environment, which carries
the FlagEmbedding and torch dependencies the root one does not:

```
.venv/bin/python -m unittest test_validation_fix.ValidationFixTests.test_repair_service_failure_returns_503
```

The test submits `['broken', RuntimeError('model unavailable')]`, so the first
call returns unparseable output and the repair call raises. Expected 503,
actual 502. No model, server or database is needed; the endpoint runs through
ASGI with the dependencies mocked.

## Suggested fix

Separate the two failure kinds at the point they are caught: record a batch that
failed because its payload would not parse, and let a dependency failure from
`call_ollama` propagate as the 503 the existing code already raises elsewhere.
Batch isolation should survive, so a service failure on one batch out of several
is still worth distinguishing from a service failure on all of them.

## For the thesis

T6, and the best worked example in the register of two separate points it needs
to make.

First, a fix can silently undo an earlier fix's guarantee. Batch isolation and
error-kind separation are both correct requirements and they were implemented
three weeks apart by changes that met in one `except` clause. Neither commit was
wrong in isolation.

Second, this is [LIM-006](LIM-006.md) demonstrated rather than asserted. The
regression test for the lost behaviour already existed and had been passing. It
caught the regression exactly as designed, and then nobody ran it, because
nothing runs it. The defect sat undetected from `6e394f9` on 2026-10-17 until
this register was built on 2026-11-02, and it was found by running the suite,
not by reading the code.
