## Symptom

If the process running a validation stops partway through, the job shows
"AI validation in progress" for ever. The student cannot upload a corrected
version, because the form is hidden while the submission is `PROCESSING`.
Development makes this common: `uvicorn --reload` restarts the server, and
with it the old in-process worker, on every code change.

## Root cause

`queue_worker` set a job to `PROCESSING` and committed before running it.
A process exit between that commit and the final status update left the row
`PROCESSING`, and the claim query never looked at `PROCESSING` rows again.
There was no ownership or age information used to tell a running job from an
abandoned one.

## Reproduction

```
# before the fix: start the app, submit a thesis, and restart uvicorn while
# the job is running; the job row stays PROCESSING indefinitely
```

## Fix

Two paths, both in `app/worker.py`. On SIGTERM or Ctrl+C, the worker rolls
back the job's partial work and sets it to `RETRYING` without counting the
attempt. At startup, `requeue_stale_jobs` returns any job that has been
`PROCESSING` longer than the AI-call timeout plus five minutes to the queue,
because no live job can run that long. The compose `worker` service has a
30-second stop grace period for the first path.

## Verified

A job `PROCESSING` since longer than `STALE_AFTER` is requeued; one started
now is left alone; a job cancelled mid-run is `RETRYING` with zero attempts.

## Tests

The three tests named above. They are new behaviour of a new module, so they
were red before the fix by import, and are green with it.
