# DEF-022: `heading_alignment` only ever checked for centering

**ID:** DEF-022
**Legacy:** none
**Kind:** defect
**Status:** fixed
**Severity:** major
**Class:** nl-to-rule-translation
**ODC:** Checking, Missing; trigger: Design Conformance
**Component:** `app/format_validation.py` :: `validate_format_profile`, the
`kind == 'heading_alignment'` branch, and the new `_heading_alignment` helper
**Found:** while extending the [DEF-020](DEF-020.md) fix, by checking what the
branch did for guideline wording other than `'centered'`
**Added:** 2026-11-11
**Fixed in:** commit `fc2b81c`
**Test:** `tests/test_format_validation_rules.py` :: `HeadingAlignment`
**Theme:** T1

---

## Symptom

A `heading_alignment` rule whose guideline wording was anything other than a
string starting with `'center'` — `'flush left'`, `'left-aligned'`,
`'right-aligned'` — produced no occurrences at all, no matter where the
heading actually sat on the page. A centered heading silently passed a
`'flush left'` requirement.

## Root cause

Two faults in the same branch, found one after the other in the same pass:

1. **Vocabulary.** The comparison was
   `str(expected).lower().startswith('center')`. Only `'centered'`-style
   wording was ever checked; every other value skipped the check entirely, and
   an empty occurrence list then read as `PASS` — the same fail-open shape as
   [DEF-020](DEF-020.md) and [LIM-007](LIM-007.md), just in the alignment
   branch instead of the case branch.
2. **Edge detection.** Fixing (1) requires telling left from right, which the
   original code never attempted — a non-centered heading was just bucketed as
   `'left/right'`. The first implementation compared the heading's distance to
   the two raw page edges and took whichever was smaller. On a page with
   asymmetric margins (this project's own default test page has 38.1mm left,
   25.4mm right), a long flush-left heading's measured midpoint can drift
   inside the page's true geometric center, so edge-distance comparison (and,
   initially, even a margin-unaware center check performed before the margin
   check) misread it as `'center'`.

## Reproduction

```python
# A heading whose left edge sits exactly on the left margin (108.0pt, from
# this page's 38.1mm left margin), long enough that its midpoint drifts
# toward the page's true center (297.5pt on a 595pt-wide page).
pg['lines'] = [{'text': 'CHAPTER TWO A VERY LONG RUNNING HEADING TEXT HERE',
                'bbox': (108.0, 50.0, 508.0, 64.0), 'font_size': 14.0}]
rule = {'type': 'heading_alignment', 'target': 'Chapter Heading', 'value': 'flush left', ...}
# Before the fix: FAIL | center  (misread; the heading is genuinely flush left)
```

## Fix

Added `_normalize_alignment`, a lenient substring match (`'center'`/`'centre'`
→ `center`, anything containing `'left'` → `left`, anything containing
`'right'` → `right`) so guideline phrasing beyond the literal word `'center'`
is recognised at all. Added `_heading_alignment(pg, info, bbox)`, which
replaces edge-distance comparison with margin-anchored detection: it reads the
page's own measured `margins['left_mm']`/`['right_mm']` (falling back to the
first page in the document with margin evidence, since a heading-only page can
have none of its own), converts them to points, and checks whether the
heading's left edge sits at the left-margin position or its right edge sits at
the right-margin position, within a tight ±10pt band — checked **before** the
wider ±8%-of-page-width center tolerance, since the margin match is the more
specific signal and must win first.

For a new contributor: the reason this needed two fixes instead of one is that
"is this heading centered" and "is this heading left-aligned" are not mirror
images of each other once margins are involved. Centering is a property of the
page as a whole (the heading's midpoint vs. the page's midpoint), so it is
margin-agnostic by construction. Left/right alignment is a property of the
heading relative to the *text frame*, not the *page*, so it cannot be judged
correctly without first knowing where that frame actually is — which is
exactly the measurement `pdf_utils.py` already produces for the margin rules,
reused here rather than re-derived.

## Verified

Before the fix: the reproduction above returned `FAIL | center` for a heading
whose left edge was exactly on the left margin. After the fix: the same input
returns `PASS`. A genuinely centered heading (`'centered'` rule, midpoint at
true page center) is unaffected and still passes, confirming the fix did not
just widen the left-tolerance at the expense of the existing center check.

## Tests

`tests/test_format_validation_rules.py :: HeadingAlignment`, seven cases:
flush-left/right/centered headings each passing their own rule and failing a
mismatched one, plus `test_long_flush_left_heading_is_not_misread_as_centered`
for the margin-asymmetry case above. Two of the right-aligned fixtures were
themselves wrong on the first attempt — built against the old edge-distance
heuristic's coordinates rather than the true margin position — and had to be
corrected once the margin-anchored version made the error visible by failing
them for the right reason.

## For the thesis

T1, alongside [DEF-020](DEF-020.md) and [LIM-007](LIM-007.md). Where
`DEF-020` is a guideline concept matched against the *wrong* standard-library
behaviour (`str.title()`), this one is a guideline concept the checker's
vocabulary never covered at all (anything but `'center'`), which is the purer
form of the fail-open shape: not a wrong implementation, an absent branch.
The margin-anchoring half is a different lesson, closer to T2 — a page-level
measurement (page center) and a frame-level measurement (margin position) look
interchangeable until a page's margins stop being symmetric, and only one of
the two is actually what "flush left" means.
