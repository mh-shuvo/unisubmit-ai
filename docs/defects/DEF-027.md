## Symptom

An installation started without `APP_SECRET` runs normally, with no warning,
and signs its session cookies with `change-this-secret-in-production`. The
`.env.example` value, `replace-with-a-long-random-secret`, was accepted too.

## Root cause

`app_secret` had a default in `Settings`, and `docker-compose.yml` passed
`${APP_SECRET:-change-this-secret-in-production}`. Starlette's
`SessionMiddleware` signs the cookie with that value, and the cookie holds
`admin_id` or `student_id`. Anyone who knows the default can sign
`{"admin_id": 1}` and is the first admin, usually the Super Admin.

## Reproduction

```python
from itsdangerous import TimestampSigner
import base64, json
cookie = TimestampSigner("change-this-secret-in-production").sign(
    base64.b64encode(json.dumps({"admin_id": 1}).encode())).decode()
# send as Cookie: session=<cookie> to an installation without APP_SECRET
```

## Fix

`app_secret` is required, with no default. A validator rejects both published
placeholders and anything shorter than 32 characters, with a message that
gives the command to generate one. The compose file uses
`${APP_SECRET:?…}`, so `docker compose` refuses to start without it, and
`.env.example` leaves the value empty.

## Verified

Before: `Settings()` with no `APP_SECRET` succeeded with the published
default. After: it raises a validation error, as do both placeholders and a
12-character value; a 40-character random value is accepted.

## Tests

`SecretSettingsTests` (missing, placeholder, short, accepted) and
`ComposeTests.test_no_secret_falls_back_to_a_default`. All were red on the
pre-fix code and are green with the fix.

## For the thesis

indistinguishable from a configured value in production. Failing closed moves
