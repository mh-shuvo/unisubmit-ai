# LIM-003: one Ollama instance is a shared serial resource with no admission control

**ID:** LIM-003
**Legacy:** none (discussed under D8 in `docs/validation_defects_and_fixes.md`)
**Kind:** limitation
**Status:** open
**Severity:** major
**Class:** resource-contention
**ODC:** n/a (limitation)
**Component:** `ai_service/main.py` :: `call_ollama`, `app/main.py` :: `queue_worker`
**Found:** the residual constraint left standing by [DEF-015](DEF-015.md)
**Added:** 2026-10-27
**Fixed in:** not fixed
**Test:** none
**Theme:** T5

## Statement

Generation is serialised by a single Ollama instance. The web application's
`queue_worker` is the intended sole consumer, but that is a convention rather
than an enforced invariant: `test_job.py` calls `process_job()` inline and
bypasses the queue, and nothing prevents a second caller from appearing.

[DEF-015](DEF-015.md) widened the timeouts so that serialised work completes.
It did not make the serialisation explicit.

## Consequence

Running `test_job.py` while the application worker is live still saturates the
queue, and both runs are slow or time out. The documented mitigation is to stop
the worker first or to submit through the UI instead, which is a procedure, not
a safeguard. It is also why the reproduction instructions in
`validation_defects_and_fixes.md` carry a warning rather than a command.

## What closing it requires

Admission control on the AI service, so that generation requests queue
explicitly and a caller is told it is waiting rather than discovering it by
timing out. A single-slot semaphore around `call_ollama` with a queue depth in
the response would be enough to turn the failure mode from a timeout into a
wait.

## For the thesis

T5. A local LLM deployment has a concurrency model whether or not the
application acknowledges one, and a timeout is what an unacknowledged
concurrency limit feels like from outside. Relevant to any claim about the
system's throughput, which is currently a property of how it is operated rather
than of how it is built.
