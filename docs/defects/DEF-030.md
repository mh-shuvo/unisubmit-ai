## Symptom

On any network the demo laptop joins, other machines can reach PostgreSQL on
5433 with user `unisubmit` and password `unisubmit`, Qdrant on 6333 with no
API key, and the AI service on 8001.

## Root cause

Compose `ports` entries without a host address bind to `0.0.0.0`. The
database password was a literal in the compose file and in the app's
`DATABASE_URL`, and Qdrant ran without its API key.

## Reproduction

```
docker compose up -d     # before the fix
docker ps --format '{{.Names}} {{.Ports}}'
# unisubmit_ai-db-1 0.0.0.0:5433->5432/tcp, ...
psql -h <laptop-ip> -p 5433 -U unisubmit unisubmit   # from another machine
```

## Fix

Every published port is bound to `127.0.0.1`. `POSTGRES_PASSWORD` and
`QDRANT_API_KEY` are required (`${…:?…}`) with no default, Qdrant runs with
`QDRANT__SERVICE__API_KEY`, and the AI service sends the key. The AI service
container moved behind the `ai` profile; for the Mac demo it runs natively,
bound to `127.0.0.1` ([LIM-008](LIM-008.md)).

An existing `pgdata` volume keeps the password it was created with
(`unisubmit`), so `POSTGRES_PASSWORD` must match it until the password is
rotated with `ALTER USER`.

## Verified

Before: four services on `0.0.0.0`, a literal password and no Qdrant key in
the compose file. After: `docker compose config` resolves every published
port to `127.0.0.1`, and compose refuses to run while any of the four secrets
is unset.
