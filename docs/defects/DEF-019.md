## Symptom

A genuinely bold heading reported "Not bold". The inverse rule,
`body_regular_required`, could never fire at all.

## Root cause

`_norm_font` collapses `TimesNewRomanPS-BoldMT` to the family name
`Times New Roman` so that font-name rules can match. `heading_bold_required`
then searched that normalised name for the substring `bold`, which the
normalisation had just removed. The weight was present in the PDF and destroyed
before the only consumer that needed it.

`body_regular_required` had the same cause with the opposite symptom: looking
for the absence of a substring that was always absent, it could never fail.

## Fix

Record `bold` and `italic` from the PyMuPDF flag bits in `inspect_pdf`, before
`_norm_font` runs. Add `_span_is_bold` and `_span_is_italic`, which prefer the
recorded flag and fall back to the font name, so callers that do not go through
`inspect_pdf` keep working. `_norm_font` itself is unchanged.

## Verified

Bold headings pass and regular headings still fail. Part of the 39 PASS /
1 WARNING to 40 PASS / 0 WARNING result on submission #3.

## Tests

`tests/test_format_validation_rules.py :: FontWeightDetection`, five cases
covering the recorded flag, the font-name fallback and both rule directions.
Confirmed red by reverting only this fix.

## For the thesis

T2. Normalisation is lossy by design, and the loss is correct for the consumer
it was written for. The defect is one of ordering and ownership: a derived
representation reached a consumer that needed the attribute the derivation had
discarded. The fix extracts the attribute before normalising rather than
weakening the normalisation, which is the generalisable move.
