## Symptom

A double-click on "Submit" on `/submit` creates two submissions with the same
title, program and file, each with a queued validation job. The student sees
both on the dashboard, and the model validates the same document twice.

## Root cause

`submit` always inserts a new `Submission` before calling
`save_queue_version`. The DEF-026 lock is per submission, so it cannot see a
duplicate of a submission that does not exist yet, and there is no key to
recognise two requests as the same upload.

## Reproduction

```
# log in as a student, fill in /submit, and double-click Submit
# the dashboard lists two submissions with the same title
```

## What closing it requires

A content key: the SHA-256 of the uploaded PDF, so an identical upload by the
same student for the same template version within the active-job window
returns the existing submission. That needs a new column and therefore a
migration ([DEF-039](DEF-039.md)); it is task P3.8 of the restructuring plan.

## For the thesis

T7. Idempotency has to be designed per entry point: the guard added for
resubmissions does not transfer to first submissions, because the thing the
lock protects does not exist yet when the duplicate arrives.
