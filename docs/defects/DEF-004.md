## Symptom

A Qdrant compatibility warning at startup, and retrieval that depended on a
server API that the deployment might not provide.

## Root cause

`query_points` was used without a version check. That API arrived in Qdrant
server 1.10, while the installed Python client was 1.19.1, and the server
version was never verified. The client version says nothing about what the
server supports, which is the drift the code assumed away.

## Fix

Keep the compatibility check enabled. Fall back to legacy dense search only when
the query API is genuinely unavailable, and only after confirming the collection
exists. Newer clients without `search()` use the legacy REST endpoint with an
optional `QDRANT_API_KEY`. Authentication failures, vector mismatches and other
errors do not trigger the compatibility fallback, so a real error is not hidden
behind a retry on an older path.

## Verified

Three of the offline tests cover the modern path, the legacy REST path with a
new client, and the case where a missing collection must not be mistaken for an
old server.

## Tests

`ai_service/test_validation_fix.py :: ValidationFixTests.test_modern_qdrant`,
`test_legacy_rest_with_new_client`, `test_missing_collection_does_not_fallback`.

## For the thesis

T5. The second-order defect is more instructive than the first: a fallback that
triggers on any error converts a diagnosable failure into a silent degradation.
Narrowing the fallback condition was the larger part of the fix.
