# LIM-007: `body_alignment` had no deterministic validator

**Added:** 2026-11-11

## Statement

The guideline parser (`ai_service/main.py`) already lists `body_alignment`
(for example, `'justified'`) as a supported deterministic rule type, but
`format_validation.py` had never implemented a checker for it. Any such rule
fell into the generic "unsupported kind" branch of `validate_all_profile_rules`
and reported `NOT VERIFIED`, regardless of what the student's document actually
did.

## Consequence

Unlike [DEF-020](DEF-020.md) and [DEF-022](DEF-022.md), this did not produce a
wrong `PASS` or `FAIL` — `NOT VERIFIED` is the correct, safe response for a
rule the engine genuinely cannot evaluate, which is why this is filed as a
limitation rather than a defect. The cost was coverage, not correctness: every
guideline that specified body-text justification had that requirement silently
excluded from the compliance rate and left for manual review, with no signal
in the report that distinguished "could not check this" from "this part of the
guideline does not specify anything."

## Resolution

Closed by adding `_page_body_alignment`, which classifies a page's body
paragraphs as `justified`, `left`, `right`, or unclassifiable, from how
tightly the paragraph lines' edges sit against the page's measured left/right
margins (reusing the same percentile-based margin estimate `pdf_utils.py`
already computes for its own margin rules), and wiring a `body_alignment`
branch into `validate_format_profile` with lenient wording matching
(`'justified'`/`'justify'`, `'left'`/`'flush left'`, `'right'`/`'flush right'`).
A page with too little qualifying body text, or a guideline value this cannot
classify, still reports `NOT VERIFIED` rather than guessing — the new
validator adds coverage without weakening the fail-safe default that made this
a limitation instead of a defect in the first place.

For a new contributor: the one subtlety worth knowing before touching this
code is that checking only the right edge is not enough to tell *justified*
from *right-aligned* text — both have flush right edges by definition, and the
difference is entirely in whether the *left* edge is also consistent. The
first version of this fix checked only the right edge and would have silently
reported right-aligned body text as justified; it was caught and corrected,
in the same session, before being committed, by checking both edges against
their own margin estimate and requiring both to be tight for `'justified'`.

## For the thesis

T1, grouped with its two siblings [DEF-020](DEF-020.md) and
[DEF-022](DEF-022.md) as the same family of gap — a guideline concept the
parser can already name, that the deterministic checker could not yet act on.
It is the boundary case of that family: where the other two silently produced
a wrong verdict (`fail-open`, in spirit, even though neither entry carries that
class label), this one never did, because `NOT VERIFIED` was already the
correctly engineered fallback for an unsupported rule kind. Whether
`nl-to-rule-translation` or a new "missing capability" class best describes
entries of this shape is a judgement call the register does not yet have
enough examples to settle; `nl-to-rule-translation` was chosen here for
consistency with its siblings rather than certainty that it is the better fit.
