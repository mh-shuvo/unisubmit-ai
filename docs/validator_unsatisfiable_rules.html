Three rules no thesis can satisfy

All three bugs sit in the measurement layer, not in any student's document. Each one makes a guideline rule impossible to pass — not hard, not usually-failing, but impossible. Each is traced below as a chain of steps, every step caused by the one above it.

Bug 1 · pdf_utils.py → estimated_line_spacing

Double spacing is invisible to the measurement

12 pt font → double spacing = 24 pt gap → ratio 2.0 → above MuPDF's ~1.5 em grouping ceiling → every line becomes its own block → one line per block means no pairs → nothing measured → None → WARNING

  1. The font size is 12 pt. It is not doubled.

    Worth stating first, because it is the easiest thing to mix up. The guideline sets body text at 12 pt and that never changes. What gets doubled is the spacing between lines, not the type.

  2. Double spacing means a 24 pt baseline gap.

    "Double" is a multiple of the font size, so the distance from one line's baseline to the next is 2.0 × 12 pt = 24 pt.

  3. The rule checks a ratio, not a distance.

    It divides the gap by the font size, so a correct document reports 24 / 12 = 2.0. The checker tolerates ± 0.28, which makes 1.72 the lowest ratio that can pass — at 12 pt that is a gap of 20.64 pt.

    NumberWhat it isWhere it comes from
    2.0 the requirement Guideline §3, "Double-spacing throughout main body text" → line_spacing = 2.0
    ± 0.28 the tolerance Hard-coded: abs(det - exp) > 0.28
    1.72 lowest ratio that passes 2.0 − 0.28
    ~1.5 em not a rule at all — MuPDF's grouping ceiling (step 4) Behaviour of the PDF reader. Not specified anywhere; measured, see step 4

  4. MuPDF keeps two lines in one block only up to about 1.5 em.measured

    This is a ceiling, not a target: gaps below it group as well. Everything from 1.19 em upward stays together until the ceiling is crossed, then MuPDF decides the lines are separate paragraphs. Sweeping line-height in 0.02 steps across nine font sizes puts the ceiling between 1.41 and 1.63 × the font size:

  5. 1.72 is above the ceiling, so a passing document is always already split.

    Here the two numbers collide. To be sampled the gap must stay under about 1.5 em; to pass it must reach 1.72 em. At 12 pt, grouping stops at an 18.75 pt gap while the passing range does not begin until 20.64 pt. The same sweep checked all 31 steps for any row that is both grouped and inside the passing range:

  6. So every line becomes a block of its own.measured

    At line-height: 2 a four-line paragraph does not arrive as one block of four lines. It arrives as four blocks of one line each:

  7. One line per block means no pairs, because the code never compares across a block boundary.

    This is the step that is easiest to state wrongly. The code does handle many blocks — the outer loop visits every one. What it never does is pair the last line of block A with the first line of block B, because block_lines is emptied at the top of each block:

  8. Nothing is measured, so the rule warns instead of failing.

    line_spacings stays empty, estimated_line_spacing comes back None for every page, and the checker takes its "could not estimate" path. The result is not a wrong number but no number at all — which is why a correctly formatted thesis gets a warning rather than a failure.

Net effect

The rule has no PASS path at all. A correctly double-spaced thesis reports None on every page and gets the warning; a thesis tight enough to be measured reports 1.5 or less and gets a hard failure. This is why version 6 sits at 97.9% rather than 100%.

The fix

Break the dependency on MuPDF's paragraph grouping, which step 7 shows is the only thing standing in the way. Collect the page's lines, sort them by vertical position, and pair neighbours that overlap horizontally — then apply the existing 0.8 – 3.0 window, which already accepts 2.0. The block boundary carries no information this check needs.

One related detail worth fixing at the same time. font_size for a line is the plain mean of its span sizes, not a length-weighted one. A line mixing a 12 pt run with one short 6 pt run reports 9 pt, which inflates the computed ratio — so the measurement is gameable toward a false PASS. The replacement should use the dominant span size rather than the mean.

Bug 2 · format_validation.py → _heading_candidates

Chapter and section rules fight over the same lines

two rules, two targets → both hit one branch that ignores the target → both get an identical line list → one demands 14 pt, the other 12 pt → the windows do not overlap → FAIL whatever the student does

  1. The guideline sets two heading levels, so the parser stores two rules.

    Chapter titles at 14 pt, secondary headings at 12 pt. Each becomes its own rule with its own target, which looks exactly right:

  2. But the resolver throws the target away.

    When the target is one of three recognised phrases, the branch that runs never consults it again — it falls back to a single shared pattern:

  3. The same pattern also sweeps in the table of contents.measured

    A second consequence of discarding the target. Unlike _find_actual_heading, which deliberately skips contents pages, _heading_candidates has no such guard — so every contents entry beginning Chapter N or 1.1 is collected as a heading as well. Version 5 of the thesis shows it plainly; the trailing digits are page numbers from the contents listing, not part of any heading:

    But this is an aggravation, not the cause. It is natural to read the bug as a clash between the 12 pt contents entry and the 14 pt heading of the same chapter. It is not — the conflict survives with a single heading and no contents page at all. Two documents, both with the chapter heading set to 14 pt bold centred:

  4. So both rules receive the same lines.measured

    Not similar lists — the identical list. A one-page PDF with a single heading, asked for each target in turn:

  5. Each rule then demands a different size of that one line.

    Both compare with a tolerance of 0.7, so the same line must satisfy two windows at once — and they do not overlap:

  6. Whatever size the student picks, at least one rule fails.measured

    The same heading rendered at three sizes, checked against only these two rules:

Net effect

Any document containing a line that starts with Chapter 1 or 1.1  earns at least one mandatory failure, and no edit the student can make will clear it. The only clean document is one whose headings the resolver cannot see at all — which is exactly what the rebuilt thesis does, at the price of 8 rules reading NOT VERIFIED and the chapter numbering being dropped.

The fix

Give each level its own pattern instead of sharing one, so step 2 stops discarding the target:

  • Chapter Heading → lines matching ^chapter\s+\w+, or the chapter-title line that follows one.
  • Section Heading → lines matching ^\d+\.\d+\s — two numeric parts, not one.
  • Third Level Heading → lines matching ^\d+\.\d+\.\d+\s. Today this target matches nothing at all, because it falls through to the substring branch and no line literally contains the words "third level heading" — which is why its four rules read NOT VERIFIED.

Bug 3 · pdf_utils.py → _norm_font

A bold heading is reported as not bold

heading is genuinely bold → font name is TimesNewRomanPS-BoldMT → normalisation rewrites it to Times New Roman → the word "bold" is gone → the rule searches the name for "bold" → FAIL, always

This one is dormant in the delivered thesis, because bug 2 leaves the rule with no headings to examine at all. It matters because of the order of operations: the moment you fix bug 2, this one starts failing.

  1. The heading really is bold in the PDF.measured

    Chrome embeds the bold cut as its own face and sets the bold flag bit, so the information is unambiguously present in the file:

  2. Normalisation rewrites the font name to the family.

    _norm_font() exists to make font comparison tolerant, so that TimesNewRomanPSMT and a dozen other spellings all match the guideline's "Times New Roman". It does that job correctly. The side effect is that every weight and style collapses to the same string:

  3. But the rule looks for the word "bold" in that name.

    The only test for weight is a substring search against the normalised name — the one string from which the weight has just been removed:

  4. So the check can never succeed.measured

    Running the rule against the genuinely bold heading from step 1:

Net effect, and why the order matters

Right now this rule reads NOT VERIFIED, hidden behind bug 2. If you fix bug 2 on its own, the Chapter Heading rules resolve to real chapter headings and three of the four start passing — alignment, size and case — while this one turns into a new mandatory failure. So bugs 2 and 3 should be fixed together, or the first fix will look like a regression.

The fix

Keep the weight when normalising. Carry the span's flags into the span record in inspect_pdf() and test flags & 16 for bold, or store the raw font name alongside the normalised one and search that instead. Either way the family-matching behaviour of _norm_font() stays as it is.

The same cause has an opposite effect elsewhere. body_regular_required flags body text as non-compliant when it finds "bold" or "italic" in a span's font name. Since those words never survive normalisation, that rule can never fire — body text set entirely in bold italic would pass it. It is not in the active profile today, but it would be wrong if switched on.

While you are in there: three rules that always pass

Not bugs in the same sense, but they report confidence the engine has not earned. The checker only recognises some of the vocabulary the guideline parser produces, and silently approves the rest.

The first two are the riskier pair: a student whose chapter headings are lowercase, or whose section headings are centred, is told the rule is satisfied. Matching 'uppercase' and 'flush left' to the existing branches is a few lines of work.

What I would do

Bug 2 is the one that matters. It penalises students for following the guideline — numbering chapters is required by rule D4, and doing it guarantees a failure nobody can clear. Every future submission hits it.

Bug 1 is cosmetic by comparison: submissions still pass, they just carry a warning that cannot be cleared and a compliance rate that cannot reach 100%. Worth fixing, but it blocks nobody.

Bug 3 is not optional once bug 2 is done — fix them in the same change, or the chapter-heading rules will swap one failure for another.

All three are small, contained changes across two functions, and all three are coverable by unit tests in tests/test_format_validation_rules.py using the reproduction cases above as fixtures.
