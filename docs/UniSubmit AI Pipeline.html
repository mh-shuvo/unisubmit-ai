Stage 01 · Build time

Guideline PDF থেকে active rules

এটি একবার চলে, submission আসার আগে। একই parse থেকে দুই ধরনের জিনিস বের হয়: যন্ত্র দিয়ে মাপা যায় এমন নিয়ম, আর অর্থ বুঝে যাচাই করতে হয় এমন শর্ত।

Stage 01 · ভিতরের কাঠামো

একই PDF, দুটি স্বাধীন pipeline

Admin যখন “Parse & Index Guideline” চাপে, index_guideline() পরপর দুটি pipeline চালায়। দুটোই একই raw PDF থেকে শুরু হয় এবং একটির output অন্যটিতে ঢোকে না — Qwen-এর বের করা rule কখনো embed হয় না, আর Qdrant-এ শুধু guideline-এর মূল লেখাই যায়।

প্রতিটি programme পায় আলাদা Qdrant collection — নাম তৈরি হয় slugify(department)_slugify(program)_slugify(submission_type)_slugify(template_version) থেকে, যেমন engineering_computer_science_thesis_v2024। ফলে CS-এর thesis কখনো BBA-র guideline-এর বিরুদ্ধে যাচাই হয় না।

Stage 02 · Run time

একটি submission, দুটি সমান্তরাল track

Worker একবারে একটি job নেয়। PDF থেকে text ও layout বের করার পর কাজটি দুই ভাগ হয় — একদিকে নিয়ম মিলিয়ে দেখা, অন্যদিকে RAG দিয়ে অর্থ যাচাই — এবং শেষে ফলাফল একত্র হয়।

PASS

নিয়মটি মানা হয়েছে, কোনো action দরকার নেই।

FAIL

নিয়ম ভাঙা হয়েছে। Mandatory rule হলে সরাসরি revision।

WARNING

সন্দেহজনক, কিন্তু submission আটকায় না।

NOT VERIFIED

যাচাই করা যায়নি — যেমন section খুঁজে পাওয়া যায়নি বা model উত্তর দেয়নি।

Stage 02 · ভিতরের কাঠামো

Retrieval ঠিক কীভাবে হয়

POST /rag/validate-এর ভিতরে ধাপগুলো এই ক্রমে চলে। মূল কৌশল হলো দুই স্তরের retrieval — একটি সাধারণ query, আর তার উপরে প্রতিটি requirement-এর জন্য আলাদা query।

  1. Department, programme, submission type ও template version থেকে collection name তৈরি হয়; সেই collection না থাকলে সরাসরি error।
  2. সর্বোচ্চ ৮০টি semantic requirement গ্রহণ করা হয় — Ignore বা disabled rule বাদ, duplicate merge, প্রত্যেকের জন্য stable semantic_id।
  3. প্রতিটি requirement-এর target section ধরে student PDF থেকে ঠিক ওই অংশের লেখা আলাদা করে বের করা হয় — পুরো document নয়।
  4. সাধারণ query দিয়ে Qdrant থেকে top 10 chunk আনা হয় (BGE-M3 দিয়ে query embed করে cosine similarity)।
  5. তারপর প্রথম ৪০টি requirement-এর প্রত্যেকটিকে আলাদা query হিসেবে ব্যবহার করে আরও top 3 করে আনা হয়।
  6. সব hit (page, text) ধরে dedupe হয়, score অনুযায়ী sort হয়ে top 40 রাখা হয়। একটিও hit না পেলে 404 — job তখন retry-তে যায়।
  7. Prompt-এ যায় তিনটি জিনিস: page ও score সহ approved guideline context, requirement-ভিত্তিক targeted student evidence, আর fallback হিসেবে student-এর ১৮,০০০ অক্ষর পর্যন্ত লেখা।
  8. Qwen JSON ফেরত দেয়। ভাঙা থাকলে একবারই repair prompt যায়; তাতেও না হলে 502 এবং job retry।
  9. ফেরত আসা status normalise হয়: অচেনা কিছু হলে NOT VERIFIED, আর non-mandatory rule-এ FAIL এলে সেটি WARNING-এ নামানো হয় — শুধু Mandatory FAIL-ই submission আটকায়।

Cross-cutting · Failure path

Processing error হলে কী হয়

Validation নিজেই ভেঙে গেলে (model down, corrupt PDF, timeout) job হারিয়ে যায় না — সীমিত সংখ্যক বার আবার চেষ্টা করা হয়।
